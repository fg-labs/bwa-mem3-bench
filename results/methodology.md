# Methodology

How the numbers in these results pages are produced, and how to read them. The
release pages are generated by `cli bench results` at each release bless; this
page is written by hand.

## Two kinds of speed measurement

**The arena** is the number to quote. Every aligner (the release being published,
every earlier bwa-mem3 release, bwa, bwa-mem2 and minibwa) runs on the same
dedicated on-demand host, one host per architecture, aligning `wgs-5M` (5M read
pairs) with 16 threads. The arms run interleaved, one warmup cycle and then three
measured reps, with each arm's index and the FASTQs read into the page cache
immediately before every rep. Every arm writes SAM piped through
`samtools view -u`, so no aligner gains from its own BAM writer. The ratios in the
arena tables are therefore like-for-like: same host, same inputs, same time
window.

**The sweep** runs every dataset on six AWS Batch spot instance types, all
`*.4xlarge` (16 vCPU), with `-t 16` and `-K 160000000` (a fixed batch size, so
output does not depend on the thread count). It is how the bench covers many
datasets and CPU families, but its timings are **indicative**:

- Reps of one cell can land on different spot hosts, which differ in speed. The
  Sapphire Rapids pools (c7i, m7i) are the noisiest, with rep-to-rep variation
  around 10%; the CV column shows each cell's spread.
- The bwa-mem2 and bwameth timings come from a separate run on other hosts, so
  the sweep's "vs bwa-mem2" ratio mixes code speed with host variation.
- Absolute times are not comparable between the sweep and the arena, or between
  releases benchmarked weeks apart.

All figures are **medians** across reps. Every speedup is written so that above
1 means bwa-mem3 is faster.

bwa-mem2 v2.2.1 has no Arm build, so Arm rows have no bwa-mem2 comparison.

AVX2/AVX-512 kernels; the Arm (NEON vs NEON) comparison is the like-for-like one.

## Memory and CPU

- **Peak RSS** is the process's maximum resident set size.
- **CPU efficiency** is CPU time divided by (wall time x 16 threads).
- **`PROCESS()`** is bwa-mem3's own timing of its alignment pipeline, excluding
  index loading.

From v0.13.0, bwa-mem3 can use a denser suffix-array index (`bwa-mem3 re-sa`),
which gives byte-identical output, runs faster and uses more memory. Each release
page states which index its bwa-mem3 arms used; the comparators always use their
stock index.

## Agreement

Agreement is measured with `compare-bams` (in this repository), which walks two
BAMs in lockstep (both aligners emit records in FASTQ order) and counts a
primary read as concordant when its alignment record matches: position, CIGAR,
FLAG, MAPQ and every aux tag the comparison does not ignore. When reads differ,
each is counted once under every class of difference it has, so the breakdown
can sum to more than the discordant share. A large "aux tags" share alongside
small position and CIGAR shares means reads mostly kept their placement and a
tag value changed.

Which tags each comparison ignores:

| comparison | ignored tags | why |
| --- | --- | --- |
| vs bwa-mem2 v2.2.1 | `MQ`, `HN` | bwa-mem3 adds them; bwa-mem2 does not emit them. |
| `--compat` vs bwa-mem2 | none | `--compat=bwa-mem2` promises identical output. |
| vs the previous release | none | Same aligner; any difference is a real change. |
| Arm vs x86 | none | Same release on two architectures. |
| `--fast` vs default | `XS`, `XA`, `SA`, `HN`, `MQ` | `--fast` prunes the candidate alignments on purpose, so tags describing the candidate set differ by design. Tags describing the chosen alignment (`AS`, `MD`, `NM`, `MC`) are compared. |

**Methylation** is compared against bwameth using **confident relocation**
instead of whole-record concordance: the share of primary reads that either
aligner maps at MAPQ >= 20 which the two place at a different locus. The two
aligners score bisulfite reads differently by design, so record concordance
mostly measures that scoring difference. Releases benchmarked before the metric
existed show it as not measured.

## Accuracy

Reads are simulated from GRCh38 with known origins
([holodeck](https://github.com/fg-labs/holodeck)), aligned by each
aligner, and graded against the truth. The `-place` sets measure placement and
MAPQ calibration; the `-vars` sets carry variants, and the MD/NM columns give
the share of variant-bearing reads whose MD/NM tag matches the truth. Methylation
sets are bisulfite-converted and compared against bwameth.

## Thread scaling

One c8g.16xlarge host (64 vCPU) runs `wgs-5M` at 1, 2, 4, ... 64 threads, 3
reps each, in a single job so every rung shares the host. Efficiency is
`T(1) / (n x T(n))` on bwa-mem3's `PROCESS()` time. bwa-mem3 overlaps FASTQ
reading with alignment, so this is pipeline efficiency, which slightly
understates pure kernel scaling at high thread counts.

## What is not published

Per-rep rows, host identifiers, spot prices and the smoke-test datasets stay in
the bench database. The `wgs-5M-alt` sweep is single-rep by design and marked as
such. To regenerate everything, see `docs/RELEASE.md` and `cli bench results`.
